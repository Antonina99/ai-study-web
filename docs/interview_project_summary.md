## 项目卡片

- **项目定位**：把长课程转写文字整理成可阅读、可追溯、可测评的学习资料，并按求职方向组织课程路径。
- **适合展示的能力**：AI 应用产品设计、长文本处理、数据质量治理、LLM 接入与失败降级、Python 应用交付。
- **实现方式**：Python、Streamlit、streamlit-shadcn-ui、OpenAI 兼容 SDK；标准库解析 DOCX；JSON 解析缓存；Streamlit Community Cloud 部署。
- **当前规模**：5 个求职方向、5 个课程模块、46 门规划课程，其中 15 门已绑定真实原文，共 4,575 个原文片段。规划课程数不等于已上线内容数量。
- **本轮可验证交付**：15 门课程均接入来源指纹匹配的复核学习版，共 369 个主题；固定回归 38 项通过（含页面交互）。其余 14 门的独立学习版冷复核已完成，57 个未确认转写词仍保留原稿并标记待核；没有音频级逐字校对。
- **个人贡献口径**：从对话可确认，你提出需求、决定产品方向、验收并反馈质量问题，使用 AI 编程协作完成迭代。具体编码、测试和清洗大量由 AI 辅助执行，面试中应按实际参与程度描述，避免说成独立手写全部代码。
- **证据可信度**：功能与结构有代码、测试和提交记录支撑，可信度高；实际用户使用效果没有统计，不能宣称商业验证或学习效率提升百分比。

## 可直接放入项目库的介绍

围绕长课程转写稿阅读成本高、摘要容易混入闲聊与错误术语、学习和练习脱节的问题，我主导需求与迭代验收，并借助 AI 编程工具落地了一套课程学习工作台。系统将 DOCX 原文和导读解析为带时间戳的课程与章节，以岗位课程路径组织学习入口，提供课程精华、原文检索、带引用的 AI 问答、课程测评及错题复习。

实现上采用 Streamlit 与分层 Python 架构，统一模型调用出口，并为课程整理和测评设计规则降级。针对长文本和生成内容质量问题，引入章节分块、均衡取样、源内容指纹、引用白名单、术语校订与学习版资产机制。原文保持不变，清洗结果单独管理，资料变化后旧校订失效，避免错误摘要持续传播。

目前项目已接入 15 门真实课程、4,575 个原文片段，并部署到 Streamlit；代码中包含解析、章节范围、引用校验、离线测评及页面交互等自动化回归。项目仍处于个人工具验证阶段，尚无活跃用户、留存率或学习提升的量化结果。

## 90 秒讲述版本

“这个项目来自我自己的课程学习需求。长课程转成文字以后，直接阅读很费时间，而自动导读还会混入闲聊、重复章节，甚至把 RAG 全称写错。我希望把这些资料整理成能学习、能追溯、还能练习的工作台。

我先把范围收敛到文字学习，取消音视频播放，围绕课程精华、岗位路径、问答和测评建立闭环。实现采用 Python 和 Streamlit，利用 AI 编程工具协作开发；我负责需求选择和持续验收。关键设计有三个：第一，长文本按章节分块，避免只处理开头；第二，回答引用必须落到真实原文编号，并由本地回填原文；第三，原文和学习版分开，校订绑定源内容指纹，资料更新后旧版本不会继续套用。

目前已经接入 15 门课、4,575 个原文片段并部署上线。最有价值的收获是，AI 学习工具的质量不只取决于提示词，更取决于数据边界、证据链和失败时的处理。下一步我会先建立小规模人工标注评测集，再考虑向量检索和长期学习记录。”

## STAR：发现错误摘要后建立内容质量链路

**Situation**：自动生成的 RAG 导读出现错误全称；长课程还存在闲聊进入摘要、问答附录重复计为章节的问题，内容可能误导学习者。

**Task**：在保留原始课程证据、不扩大技术栈的前提下，修正学习内容并让修正能够持续生效。

**Action**：定位错误发生在导读而非对应原文，检查 DOCX 解析边界；将术语纠错、课程事务过滤和重复内容处理区分开；对相似句去重增加数字、否定与比较符号保护；为经语境复核的课程建立单独学习资产，记录时间戳、原文编号和来源指纹；生成引用只允许来自本地候选集合，展示时重新读取原文；补充自动化回归，防止解析或课程切换再次造成串课。

**Result**：RAG 课程学习版整理为 26 个有出处的主题；修复导读 40 个章节被重复解析为 80 个章节的问题；其余 14 门已按全文语境和独立学习版复核流程整理为 343 个主题，全部 15 门接入网页，38 项回归通过；原始 DOCX 未被覆盖。测试能验证结构和程序行为，不能证明所有知识结论绝对正确。

**经验沉淀**：正确的原文仍可能生成错误的摘要，因此必须分别验证“提取是否正确”和“总结是否忠实”。原文引用存在，只证明出处可找到，并不自动证明该引用支持结论。

**适用问题**：如何处理模型幻觉、如何设计可追溯系统、怎样定位数据质量问题、如何通过用户反馈迭代产品。

## 技术追问与回答要点

### 这是 RAG 项目吗？用了向量数据库吗？

实现了“从课程原文检索相关证据，再提供给模型回答”的检索增强思路。目前检索是关键词与中文子串的词频加权匹配，限制在所选课程或章节内；没有 Embedding、向量数据库、混合召回或重排模型。可以称为课程知识检索增强问答原型，不应包装为已实现成熟向量 RAG 平台。

### 如何处理长文本？

课程先分章节，超长章节再拆成块；模型逐块萃取，部分成功可复用、失败块可重试；聚合时兼顾各块，上下文采用均衡取样。用于模型的上下文仍有长度上限，不能声称每次回答都会读取整门课的全部原文。

### 怎样防止虚构引用？

本地为原文生成 `original-N`，检索返回候选白名单，模型只能引用候选编号，返回后再次校验。界面中的证据正文由本地知识库回填。这个机制能拦截不存在的编号，但还需要评估“引用存在却不支持结论”的语义问题。

### 模型调用失败怎么办？

同步请求有超时与有限次数重试；现有等待间隔随尝试次数线性增加，不是严格指数退避。课程测评可回退到当前课程文字题，再到通用题库。原文阅读和离线学习不依赖 API Key，AI 助教本身仍需要有效 Key。

### 怎样避免旧缓存污染？

DOCX 解析缓存带解析版本，文件变化触发重新解析；AI 整理缓存区分课程源内容与模型；经复核学习资产绑定原文和导读的 SHA-256 指纹，匹配才使用。缓存失效解决版本一致性，不能代替内容事实核验。

### 为什么用 Streamlit？有什么限制？

对以文字、表单和学习流程为主的个人原型，纯 Python 可以减少前后端交付成本。业务逻辑仍放在 `core/`，页面放在 `views/`。当前没有独立 API 服务、账号体系、持久化学习数据库或多租户能力；学习进度和错题只存在 Session State，错题通过 JSON 导出备份。

### 如何证明效果？

当前可证明的是课程入库数量、原文片段规模、功能行为和具体修复案例；自动化测试不是真实用户效果评估。后续建议人工标注课程问题集，分别评估检索召回、回答正确性、引用支持度和未回答率，再记录任务完成时间与用户反馈。尚未测量的数据不写成成果。
